## 项目背景

Platform Portal 是一个采用前后端分离架构的企业内部管理平台，包含组织架构、人员、合作伙伴和活动管理等业务模块。

我目前主要参与 **Structure** 与 **Org Chart** 相关功能的开发和维护。进入项目后，我首先梳理页面、业务组件、Pinia 状态管理和后端 RESTful API 之间的数据流，以理解现有模块的职责边界和交互方式。

- 依赖安装和锁定版本相关问题；
- TypeScript 类型检查；
- Stylelint 与其他代码检查工具配置；

这部分工作让我更清楚地认识到，能够稳定复现项目环境，是理解和修改已有企业项目的第一步。

## Org Chart 节点展示优化

原有组织架构树会在部分数据结构下显示冗余的 Structure 根节点。我根据节点层级、父子关系和子节点数量调整了前端展示逻辑，使页面在满足条件时隐藏冗余根节点。

实现过程中需要特别保证：

- 只调整展示层，不修改原始业务数据；
- 不影响节点编辑功能；
- 不破坏原有层级关系；
- 在不同组织结构数据下保持稳定表现。

这项工作让我进一步理解了“展示模型”和“业务数据模型”应该保持分离的重要性。

## Org Chart Preview 与路由设计

我为 **Structure Detail** 和 **Structure List** 增加了 Org Chart Preview 入口。用户可以通过动态路由参数打开指定 Structure 对应的只读组织架构页面。

Preview 页面可能来自列表页，也可能来自详情页。为了让返回行为符合用户预期，我使用路由 Query 参数记录进入来源：

- 从 Structure List 进入，返回列表；
- 从 Structure Detail 进入，返回对应详情；
- 直接访问 Preview URL 时，使用默认返回路径。

我还检查了 Preview 入口与只读模式、编辑模式及路由权限之间的关系，避免 Preview 按钮在只读页面中重复出现。

## Preview 工具栏适配

在不同屏幕宽度和浏览器缩放比例下，Preview 工具栏可能出现空间不足或布局不平衡的问题。

我通过只读模式的条件样式调整工具栏布局，在不改变编辑页面交互的前提下，改善 Preview 页在不同显示环境中的表现。

## Duplicate Structure

我扩展了 Structure 的 **Status & Actions** 菜单，在状态操作和危险操作之间加入 **Duplicate Structure** 功能，并复用项目已有的克隆 API。

除了触发复制请求之外，这项功能还需要考虑完整的异步交互流程：

1. 操作前显示确认弹窗；
2. 请求期间显示 Loading 状态；
3. 防止用户重复提交；
4. 成功后提供明确反馈；
5. 失败时显示错误信息并处理异常；
6. 根据当前页面决定如何更新缓存数据。

## 缓存更新策略

复制操作完成后，不同页面需要采用不同的数据更新方式：

- **Structure List：** 强制刷新列表，以新数据覆盖当前缓存；
- **Structure Detail：** 将相关缓存标记为失效，确保后续访问时重新获取最新数据。

这让我意识到，缓存策略不能只考虑“是否重新请求”，还需要结合当前页面、用户下一步行为和数据一致性要求进行设计。

## Org Chart 缩放快捷键

在原有缩放交互基础上，我为 Org Chart 增加了 **Alt/Option + 鼠标滚轮**快捷键，并补充了对应的中英文提示文案。

实现时需要兼顾 Windows 与 macOS 的按键差异，同时确保新增快捷键不会破坏既有的画布滚动、节点操作和浏览器交互。随后我继续调整了缩放上下限、Fit Screen 行为和画布拖动边界，使大型组织架构图在不同缩放状态下更容易定位和浏览。

## Org Chart Minimap

为了帮助用户理解大型组织架构图中的当前位置，我设计并实现了独立的 **Minimap** 组件。Minimap 会以缩略形式展示完整组织结构，并通过视口框标识主 Org Chart 当前可见的区域。

目前支持的交互包括：

- 节点展开、收起或状态变化后自动更新缩略图；
- 根据主画布的移动和缩放同步更新当前视口范围；
- 拖动 Minimap 中的视口框，同步平移主 Org Chart；
- 保持当前缩放比例及原有画布交互逻辑不变；
- 配合横向和纵向布局切换重新计算内容范围。

## Minimap 更新与性能控制

由于 Org Chart 的节点结构、容器尺寸和变换状态都可能发生变化，如果每次 DOM 变化都立即完整重绘 Minimap，会产生大量重复计算。

我将 Minimap 封装为职责独立的组件，并结合以下浏览器能力控制更新时机：

- `MutationObserver`：监听组织架构节点及相关 DOM 状态变化；
- `ResizeObserver`：响应主画布和容器尺寸变化；
- `requestAnimationFrame`：将同一帧内的多次更新合并到浏览器绘制周期中。

这种方式让 Minimap 能够及时反映主视图变化，同时减少连续操作期间的重复渲染和性能开销。开发过程中我也调整了页面布局、按钮位置、响应式尺寸和多语言显示，并完成 TypeScript 组件编译与基础代码检查。

## Approval Line 分类数据同步

这两天我完成了一次基于新版 **2026 Classifications** Excel 表的 Approval Line 数据核对与同步。任务不只是将表格内容写入系统，还需要解决页面数据范围、姓名格式差异、重名、审批人身份解析、旧数据冲突和本人审批等问题。

### 数据范围分析

员工 API 共返回 **1105 条员工记录**，而 Approval Line 页面实际显示 **438 名员工**。经过分析，我确认页面范围来自 `active + isHrVisible` 条件筛选，而不是 API 数据缺失。

在此基础上，我对比新分类表中的 Employee Name、Preferred Name 和 Level 1–4 审批关系，并将表格人员解析到数据库员工 ID。

### Excel 预处理与同步计划

我编写了预处理脚本，用于：

- 自动识别 `2026 Classifications` 的真实表头位置；
- 读取 Employee Name、Preferred Name 和 Level 1–4；
- 清理首尾空格、连续空格及隐藏字符；
- 为员工和审批人建立多种姓名别名；
- 应用经过人工确认的特殊姓名映射；
- 输出 JSON 同步计划、Excel 人工检查表和浏览器 Runner。

将“读取与规范化”“人工检查”和“浏览器写入”拆开后，每一步都可以独立复核，也避免直接根据原始 Excel 内容修改线上数据。

### 姓名匹配与安全保护

浏览器 Runner 通过已登录页面访问员工 API，并采用分层匹配策略：

1. 优先使用 Employee Name 与 Preferred Name 进行标准化精确匹配；
2. 清理大小写、称谓、空格和标点差异；
3. 结合中文名和人工别名处理特殊情况；
4. 精确匹配失败后才进入相似度匹配；
5. 相似度最低要求为 **80%**；
6. 第一候选必须比第二候选至少高 **5%**；
7. 多人匹配、重名或身份不明确时停止自动写入，转入人工审核。

写入前还会再次确认：

- 员工 ID 和审批人 ID 均真实存在；
- 双方均处于 active 且 HR 可见的状态；
- 审批人不是员工本人，避免形成审批循环；
- 默认不覆盖数据库中已有的不同审批人；
- dry-run 与正式写入使用相同校验逻辑；
- 请求之间保留短暂间隔，降低连续请求压力。

### 分阶段执行结果

我按照 Level 1–4 分批执行 dry-run、人工核对、正式写入和结果复验，而不是一次性提交全部变更。

- 第一阶段完成 **104 条**安全补录；
- 对已确认身份的人员定向补录 **18 条**；
- 通过中文名和人工身份确认补录两组共 **7 条**；
- 在明确“以新分类表为准”后，只筛选并覆盖 **82 条**已有不同审批人的记录；
- 找不到、重名、离职和本人审批记录均未参与自动覆盖；
- 最终确认或同步 **1214 条**审批记录，所有写入请求失败数为 **0**；
- 对剩余 **109 条**记录完成原因分类，为后续人工确认保留清晰依据。

任务结束后，我删除了项目中的临时同步脚本，使 Git 工作区保持干净，避免将一次性业务数据和操作工具误提交到正式代码库。

## Code Review 与回归检查

在开发和 Review 过程中，我重点检查了：

- 用户是否拥有对应操作权限；
- 只读模式是否会暴露编辑操作；
- 页面存在未保存表单时，跳转行为是否安全；
- Preview 的进入和返回路由是否稳定；
- Duplicate 是否影响原有状态与删除操作；
- 新增逻辑是否会破坏既有业务功能；
- 部署在不同基础路径下时，路由是否仍然可用。

相比“让按钮能够工作”，企业项目更重要的是确认它在权限、异常状态和既有流程中都能正确工作。
